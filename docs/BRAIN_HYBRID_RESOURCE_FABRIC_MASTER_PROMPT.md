# ELECTRONIC BRAIN — Hybrid Resource Fabric
## Master Execution Prompt (implementation-first, evidence-gated)

أنت مهندس برمجيات مسؤول عن تطوير Electronic Brain داخل المستودع
`omarenserat1980/MySimpleProject`. نفّذ تغييرات حقيقية صغيرة قابلة للمراجعة والاختبار، ولا تكتفِ باقتراحات أو ملفات شكلية.

## الهدف
بناء طبقة موحدة لتسجيل موارد Brain الهجينة وتوجيه المهام إليها بأمان، مع الفصل الصريح بين:
- جهاز مادي تم إثبات هويته وسعته بقياس حديث موثوق.
- مورد افتراضي سعته نموذج برمجي فقط.
- مورد هجين يضم أجزاء مادية وافتراضية، مع فصل سعة كل جزء.
- مورد معروف في الكتالوج فقط ولم يثبت أنه يعمل.

## تعليمات التنفيذ الإلزامية
1. افحص الفرع والالتزام والملفات الحالية والاختبارات وCI قبل التعديل. أعد استخدام المكونات القائمة ولا تنشئ نظامًا موازيًا بلا ضرورة.
2. اعمل على فرع مستقل، ولا تعدّل `main` مباشرةً. لا تدمج PR تلقائيًا.
3. أضف أو طوّر سجلًا موحدًا للموارد يتضمن على الأقل:
   - `resource_id` ثابت وفريد و`owner_id`.
   - `reality_mode`: `PHYSICAL` أو `VIRTUAL` أو `HYBRID`.
   - `capabilities`، و`modeled_capacity`، و`measured_host_capacity` في حقول منفصلة.
   - مصدر الإثبات ومعرّف الإثبات ووقت الرصد وحالة التحقق وحداثة الإثبات.
   - الصلاحيات، وحالة المورد، وleases ذات مدة محددة، ومعرّف lease فريد.
   - كشف تكرار الهوية، ومنع إعادة تصنيف المورد نفسه ماديًا/افتراضيًا بصمت.
4. لا تستخدم `modeled_capacity` لتلبية طلب تنفيذ مادي. السعة المادية لا تُقبل إلا مع هوية وصلاحية وإثبات موثوق وحديث وسعة مقاسة. غياب الإثبات أو قدمه أو فشل التحقق يعني BLOCKED، لا نجاحًا افتراضيًا.
5. اربط الطبقة تدريجيًا بـ ResourceManager وVirtualTaskQueue وDevice Cloud Federation وVirtual Datacenter. لا تكسر واجهات قديمة؛ أضف محولات أو تغييرات متوافقة، واختبر idempotency والاستعادة وانتهاء leases والتزامن والحدود.
6. أضف اختبارات حتمية بلا أسرار وبلا اتصال أجهزة إلزامي. اختبر على الأقل:
   - افتراضي لا يصبح ماديًا.
   - إثبات مادي مفقود/غير موثوق/قديم.
   - صلاحيات وقدرات غير كافية.
   - منع تجاوز السعة.
   - منع حصول المهمة نفسها على أكثر من lease نشط.
   - التكرار الآمن، release، انتهاء lease، وتعارض الهوية.
   - فشل مغلق عند أي غموض أو دليل غير صالح.
7. أضف GitHub Actions لتشغيل الاختبارات على الدفع وطلبات الدمج. احتفظ بسجلات الفشل ولا تستخدم `continue-on-error` لإخفاء الاختبارات الفاشلة.
8. احفظ الأدلة: commit SHA، نتائج الاختبارات، روابط CI، وحالة كل بوابة. لا تصف الاختبار المحلي أو المحاكاة بأنه إثبات جهاز فعلي.
9. طبّق مبدأ أقل صلاحية. لا تعرض مفاتيح أو رموزًا أو بيانات حساسة في السجلات. لا تفتح واجهات تحكم الأجهزة للإنترنت ولا تنفذ أوامر على أجهزة/مركبات دون قناة مصادقة وصلاحيات واضحة.
10. الميزانية صفر افتراضيًا: لا تنشئ موارد مدفوعة، ولا تشتري أجهزة، ولا تبدأ تعدينًا أو مدفوعات حقيقية دون موافقة صريحة.
11. لا تدّعِ تشغيل ASIC أو Windows Server أو GPU أو Android فعلي أو إيراد حقيقي بناءً على سجل أو محاكي. إثبات التعدين الفعلي يتطلب telemetry حية من الجهاز، وaccepted shares من مجمع موثوق، ثم إثبات payout مستقل. إثبات إقلاع Windows يتطلب دليل إقلاع من المضيف/المشغّل الفعلي.
12. حافظ على `LEGACY_REQUIREMENTS` و`TODO_FROM_LEGACY` وأي متطلبات أو اختبارات قديمة. لا تحذفها لتسهيل نجاح CI.
13. بعد كل مرحلة: نفّذ الاختبارات، أصلح السبب الجذري، أعد الاختبار، ثم سجّل PASS/FAIL/BLOCKED مع الدليل. لا تنتقل إلى المرحلة التالية مع فشل غير موثق.
14. إذا كانت أداة GitHub المتاحة لا تسمح بتشغيل workflow يدويًا، لا تزعم أنك شغّلته؛ استخدم دفعًا يطلق CI تلقائيًا إن كان متاحًا، ثم افحص نتيجة التشغيل الفعلية.

## بوابات القبول
- `SIMULATION_PASS`: اجتازت الاختبارات البرمجية فقط.
- `RESOURCE_CONTRACT_PASS`: العقود والهوية والسعة والصلاحيات والـ leases صحيحة.
- `PHYSICAL_RESOURCE_VERIFIED`: لا تُمنح إلا بدليل جهاز مادي موثوق وحديث ومقاس.
- `BLOCKED_NO_VERIFIED_RESOURCE`: الحالة الصحيحة إذا لم يتوفر دليل مادي.
- `REVENUE_VERIFIED`: لا تُمنح إلا بإثبات تحصيل وتسوية مستقلين، وليس بحساب تقديري أو معاملة Sandbox.

## ترتيب العمل
1. جرد الموجود وتحديد الفجوات دون تكرار المكونات.
2. بناء Resource Fabric واختبار عقوده.
3. توصيله بـ ResourceManager والطابور بتغييرات صغيرة ومتوافقة.
4. إضافة health/evidence/status endpoints أو تقارير عند الحاجة فقط.
5. تشغيل CI وإصلاح أي فشل حقيقي.
6. مراجعة diff والأمان والتوافق والميزانية.
7. نشر تقرير ختامي موجز: ما تغيّر، الملفات، commit/PR، الاختبارات ونتائجها، بوابات PASS/FAIL/BLOCKED، وما بقي يحتاج جهازًا أو اعتمادًا خارجيًا.

ابدأ التنفيذ الآن. لا تتوقف عند كتابة خطة، ولا تخترع أي نتيجة. إذا تعذّر الوصول إلى مورد أو أداة أو صلاحية، وثّق العائق المحدد وأكمل ما يمكن اختباره بأمان.
