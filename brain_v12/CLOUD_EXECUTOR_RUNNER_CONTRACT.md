# Brain Cloud Executor Runner Contract

This contract defines the only runner class allowed to execute Windows Real Boot.

## Runner labels
- self-hosted
- linux
- x64
- brain-internal
- qemu
- windows-real-boot
- brain-cloud-executor

## Trust architecture

The Brain control plane exposes an authenticated attestation API at:
- `POST /api/cloud-executor/attestation/challenge`
- `POST /api/cloud-executor/attestation/issue`
- `POST /api/cloud-executor/attestation/consume`

Every request must include `X-Brain-Executor-Token`. The server accepts only a per-executor token whose SHA-256 digest is present in the out-of-band `BRAIN_CLOUD_EXECUTOR_ENROLLMENTS_SHA256_JSON` map. The raw enrollment token must never be stored in the repository or in the server enrollment map. Use high-entropy random tokens and rotate them after suspected exposure.

The control plane requires `BRAIN_EXECUTOR_ATTESTATION_SIGNING_KEY_B64` to be injected from a protected secret store. The Ed25519 private key must remain on the Brain control plane and must never be available to a runner or GitHub Actions job. The registry DB is configured with `BRAIN_CLOUD_EXECUTOR_REGISTRY_DB`; by default it uses `BRAIN_DB`. It stores issued challenges and attestations, and atomically rejects challenge reuse and attestation replay. All runner hosts must contact the same authoritative registry service/database for consume decisions. Independent local SQLite ledgers do not provide cross-host replay protection.

## Challenge and renewal policy

- A challenge is generated by the server using a cryptographically secure random nonce and expires after 60 seconds.
- A challenge is bound to one enrolled executor ID and can be consumed once.
- The issuer signs an attestation valid for at most 300 seconds.
- The host verifies the Ed25519 signature, executor ID, audience, timestamps, and schema, then calls the central `/consume` endpoint. The central registry accepts that issued nonce once and rejects replay, expiry, and executor mismatch.
- Renew by requesting a new challenge and a new attestation. Never extend or reuse an old attestation.
- If the registry is unavailable, authentication fails, the trust key is missing, or signature/identity validation fails, the gate fails closed.

## Trust-anchor installation

Install the public key on the executor using `tools/install_brain_executor_trust_anchor.sh` through an independent trusted host-management channel. Supply `BRAIN_TRUST_ANCHOR_SHA256` using a fingerprint confirmed over a separate channel. The installer rejects a mismatched fingerprint and installs root-owned key material. The bootstrap rejects symlinked keys, non-root ownership, and group/other write permissions.

The installer has not been run on Arkan, Redmi, or any production host in this work. A repository commit is not proof that the trust anchor was installed.

## Preflight and lifecycle

The host bootstrap:
1. Verifies the host has Linux x86_64, usable `/dev/kvm`, QEMU, OVMF, and required media tools.
2. Requests a fresh challenge and signed attestation from the central Brain API over HTTPS.
3. Verifies the signature and consumes the attestation centrally before runner registration.
4. Registers the runner as ephemeral and starts it in the foreground for one job; it does not install a persistent runner service.
5. Removes the local attestation and does not persist the executor bearer token in the runner environment.

The intended lifecycle is:

`PROVISION HOST -> INSTALL TRUST ANCHOR -> FETCH FRESH ATTESTATION -> PREFLIGHT -> REGISTER EPHEMERAL -> ONE JOB -> PRESERVE EVIDENCE -> DESTROY/REPROVISION`

The control-plane API and registry code are implemented in the repository but are not deployed or configured by these commits. Configure the API only behind TLS, provision the enrollment-token hash map and private key from a protected secret store, and validate them independently before using this path.

## Required substrate and safety rules

The runner must independently provide x86_64, readable/writable `/dev/kvm`, working KVM acceleration, `qemu-system-x86_64`, `qemu-img`, `xorriso`, `wimlib-imagex`, `mkfs.vfat`, `mcopy`, OVMF, and a writable execution surface.

- Never set executor identity in workflow YAML.
- Never print tokens, private keys, owner approvals, or attestation contents.
- Never create or sign the Windows execution contract inside a workflow.
- Do not start Windows Real Boot unless the separately issued Brain execution contract passes its closed-loop authority, identity, lease, fencing, source-commit, and signature checks.
- An executor attestation proves only the claims signed by the trusted issuer. It does not prove Windows booted.
- Keep the PR in draft until the production issuer, secret injection, enrollment, independent trust-anchor installation, host preflight evidence, and complete CI are verified.
