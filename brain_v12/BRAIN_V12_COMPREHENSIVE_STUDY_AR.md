# دراسة شاملة لـ Electronic Brain V12 — الوضع الحالي وخطة التكامل والتنفيذ

**التاريخ:** 2026-10-10  
**المستودع:** `omarenserat1980/MySimpleProject`  
**فرع العمل:** `brain-software-ownership-runtime`  
**الحالة:** وثيقة هندسية ضمن فرع التطوير؛ ليست شهادة جاهزية إنتاج ولا تفويضًا لتغييرات سحابية مدفوعة.

## 1. الخلاصة التنفيذية

برين ليس مجرد قائمة أدوات؛ السورس يستورد وحدات للإدراك والذاكرة والتخطيط والقرارات والمهام والذكاء الاصطناعي والأدوات والمزامنة وإدارة الأجهزة وGit والوسائط والفرص الاقتصادية والبنية الافتراضية واكتشاف Windows Cloud. التحدي الرئيسي هو تحويل هذه الوحدات إلى **منظومة واحدة ذات عقود واضحة، وهوية تنفيذ معروفة، وصلاحيات محدودة، وأدلة مستقلة، واستعادة قابلة للاختبار**.

وجود ملف أو مسار API لا يثبت أن الخدمة متصلة أو أن المنفّذ متاح أو أن عملية نجحت. كل شاشة أو تقرير يجب أن يميز بوضوح بين:
- **مخطط:** هدف مطلوب، لا دليل على وجوده.
- **مسجل:** بيانات وصفية أدخلت إلى النظام.
- **مكتشف:** نتيجة فحص قراءة فقط مع المضيف والتوقيت والمصدر.
- **منفذ:** سجل يوضح الأمر المسموح والمنفّذ والنتيجة.
- **متحقق مستقلًا:** دليل أعاد فاحص موثوق التحقق منه.
- **جاهز:** جميع بوابات القبول المطلوبة ناجحة وحديثة.

لا ينبغي تمكين التثبيت أو التشغيل أو النشر لمجرد أن العنصر ظهر في الكتالوج أو أن المنفذ أعاد `ok=true`.

## 2. خريطة المنظومة حسب ما ظهر في السورس

### أ. طبقة الواجهة وواجهة API
ملف `brain_v12/app.py` يجمع FastAPI ووحدات متعددة، ويعرّف واجهات لإدارة البرامج ويستخدم `require_control_key`. هذا يعطي نقطة دخول موحدة، لكنه يجعل الملف الكبير نقطة اقتران مركزية؛ يجب نقل مجموعات المسارات إلى routers مستقلة تدريجيًا، مع اختبارات عقود لكل مجموعة.

### ب. الإدراك والاستدلال والقرار
توجد وحدات مثل `CognitiveLoop` و`CognitiveOrchestrator` و`DecisionEngine` و`ProblemSolver` و`BrainCouncil`. المطلوب أن تنتج هذه الطبقة **خطة مفسرة** لا تنفيذًا مباشرًا: هدف، افتراضات، مخاطر، خيارات، شروط توقف، معايير قبول، وموافقة مطلوبة.

### ج. الذاكرة والحالة الدائمة
توجد `MemoryStore` ومخازن مزامنة ومهام وسجلات أدلة. التحديات الواجب حسمها: فصل ذاكرة المحادثة عن الحالة التشغيلية وعن الأدلة غير القابلة للتلاعب، وسياسة ترحيل قاعدة البيانات، والنسخ الاحتياطي والاستعادة، والتعامل مع التزامن وتكرار الطلبات.

### د. الوكلاء والأدوات وتغيير الشيفرة
توجد وحدات Code Agent وCode Tool وWorkspace وEngineering Team وPlugin Manager وBrain Git/Workflow. يجب أن تمر تغييرات الشيفرة دائمًا عبر: فحص الحالة الحالية، خطة diff، اختبارات محددة، مراجعة، موافقة عند التغيير ذي الأثر، تنفيذ، فحص diff النهائي، ثم دليل محفوظ. لا ينبغي لوكيل كتابة الشيفرة امتلاك صلاحية نشر أو تعديل أسرار لمجرد امتلاكه صلاحية اقتراح تعديل.

### هـ. العمال والأجهزة والتنفيذ عن بعد
توجد `DeviceBridge` و`WorkerRegistry` و`WorkloadRouter` و`TaskSyncAdapter` ووحدات المراقبة. يجب تعريف عقد موحد لكل منفذ يتضمن هوية ثابتة، heartbeat حديثًا، قدرات معلنة ومثبتة، حدود موارد، مهلة، بصمة نسخة العامل، ومعرّف مهمة/idempotency. لا يكفي تسجيل الهاتف أو العامل أو ظهوره أخضر لإثبات تنفيذ حقيقي.

### و. البرامج والأنظمة
أُضيف في هذا الفرع سجل SQLite وكتالوج مطلوبات للبرامج وواجهات API محمية. الكتالوج يصف المطلوب ولا يكتشف المضيف بعد. جرى تصحيح هدف Python إلى `installed` بدل `running`، كما شُددت قاعدة التحقق كي لا تستطيع واجهة الملاحظة إعلان `verified` اعتمادًا على رابط يرسله العميل فقط. لا يوجد في هذا التغيير مثبت حزم أو منفّذ أوامر.

### ز. Windows Server 2025 وAzure
يحتوي المستودع على مسار workflow للتهيئة السحابية، وسكربتات preflight/deploy، وآليات اكتشاف/تحقق Windows Cloud. الـ workflow يطلب `approve_apply` صراحة قبل خطوات إنشاء الحالة البعيدة أو نشر الموارد؛ هذه الخطوات لا ينبغي تشغيلها أثناء تدقيق المصدر فقط. وجود القالب أو workflow لا يثبت أن VM موجودة أو أقلعت. المطلوب إثبات مستقل من Azure Resource Manager، وحالة تشغيل VM، ودليل من داخل نظام الضيف، ثم اختبار دخول آمن.

### ح. الذكاء الاصطناعي والتكاملات
توجد بوابة AI وموجّه نماذج ومزودون وتكاملات. يجب وضع سياسة بيانات موحدة: تصنيف الحساسية، الحد الأدنى من السياق المرسل لكل مزود، مهلة وإعادة محاولة، سقف تكلفة، سجل مزود/نموذج/إصدار، وعدم إرسال مفاتيح أو سجلات خاصة إلى النماذج. يجب أن يظل النموذج مستشارًا، لا مصدر صلاحيات.

### ط. المراقبة والتحقق
توجد وحدات `BrainSupervisor` و`BrainSelfMonitor` و`VerificationEngine` و`EvidenceStore` واكتشاف Windows Cloud. هذه أساس جيد، لكن يجب ربطها بعقود واحدة. التحقق من hash لسجل يثبت سلامة ذلك السجل فقط، ولا يثبت وحده أن نظام التشغيل أقلع أو أن التطبيق يعمل وظيفيًا.

## 3. مواطن القوة

1. وجود وحدات متعددة تغطي دورة العمل من الإدراك إلى التنفيذ والتعلم.
2. وجود مفاهيم للصلاحيات والمراقبة وسجل الأدلة والتحقق.
3. استخدام GitHub كمصدر شيفرة وسير عمل للاختبارات.
4. وجود مسار سحابي منفصل لـ Windows Server مع بوابة موافقة صريحة في workflow.
5. بدء سجل برامج دائم وكتالوج desired-state بدل الادعاء بأن البرامج مثبتة.
6. حماية واجهات سجل البرامج بمفتاح التحكم الموجود.
7. إمكان بناء تكامل تدريجي دون منح الهاتف أو النموذج وصول shell مفتوحًا.

## 4. مواطن الضعف والمخاطر التي تحتاج إثباتًا أو معالجة

### P0 — صحة الادعاءات والثقة
- لا يُسمح بتحويل `planned` إلى `ready` بناء على إدخال بشري أو URL غير مفحوص.
- يجب ربط كل دليل بهوية المضيف، وتوقيت الفحص، ونسخة العامل، ومصدر النتيجة، وhash المحتوى، ومدة صلاحية.
- يجب رفض الأدلة القديمة أو المفقودة أو المنقولة من مضيف آخر.
- يجب الفصل بين «نجاح الأمر» و«تحقق الهدف».

### P0 — الصلاحيات والأسرار
- مفتاح التحكم المشترك مناسب كبداية محدودة، لكنه ليس نموذج صلاحيات كاملًا؛ المطلوب هويات منفصلة لكل عامل، وصلاحيات scopes، وتدوير مفاتيح، ومنع إعادة الاستخدام، ومراجعة الوصول.
- لا تطبع الأسرار في logs أو الأدلة أو رسائل الخطأ.
- لا تنفذ أوامر عامة من مدخلات المستخدم أو محتوى النموذج.
- يجب أن تكون إجراءات Azure/النشر/التثبيت/الحذف/الإنفاق موافقات منفصلة ومحددة النطاق.

### P0 — مسار Windows Cloud
- التحقق من مصدر شهادة WinRM وهوية المضيف؛ تجنب تخطي التحقق من CA أو اسم المضيف في الإنتاج.
- تأكيد تقييد الشبكة على مصدر موثوق، وعدم فتح RDP للعالم، وتفضيل Bastion/VPN أو وصول مُدار عند توفره.
- مراجعة صلاحيات OIDC وAzure RBAC ونطاق الاشتراك ومخزن Terraform state.
- فصل `plan` عن `apply` وتخزين artifact الخطة ومراجعتها، مع منع drift غير المتوقع.
- التحقق من اسم الصورة، نوع الترخيص، حجم VM، الأقراص، التكلفة، وعناوين الشبكة قبل أي إنشاء.
- يجب إثبات وجود المورد فعليًا بدل استنتاجه من نجاح workflow أو إعدادات GitHub.

### P1 — سلامة التنفيذ والتعافي
- لا يوجد دليل من هذا التغيير وحده على وجود sandbox فعلي أو عزل شبكة/نظام ملفات لجميع العمال.
- يجب فرض مهلات وحدود CPU/RAM/disk/output، وتحديد egress، وقائمة أوامر/عمليات مسموحة.
- دعم idempotency ومنع تنفيذ المهمة مرتين، وقفل لكل مورد، وcancel/timeout آمن.
- إنشاء نسخة احتياطية قابلة للاستعادة واختبار rollback قبل تغييرات الحالة.
- عدم تشغيل عدة workflows متضاربة على نفس العامل أو المورد.

### P1 — المعمارية والتكامل
- ملف `app.py` نقطة اقتران كبيرة؛ يجب فصل routers والخدمات دون إعادة كتابة جماعية.
- توحيد نماذج Task وWorker وEvidence وSoftware وCloudResource وإصدارات API.
- تحديد مالك canonical لكل وظيفة لمنع تكرار منطق متشابه في V7/V12 وواجهات Cloud.
- توحيد حالات المهمة: `proposed → approved → queued → running → completed/failed/cancelled → independently_verified`.
- توحيد الارتباط بين `task_id` و`run_id` و`commit_sha` و`worker_id` و`evidence_id`.

### P1 — الاختبارات والمراقبة
- كل ميزة تحتاج اختبارات وحدة، واختبارات API وصلاحيات، واختبارات فشل، وتكامل، واختبارات تراجع.
- الاختبارات غير المرتبطة بالميزة قد تفشل بسبب عيوب قديمة؛ يجب تصنيفها لا تجاهلها.
- لا يُدمج PR إذا كانت بوابات القبول المطلوبة معلقة أو فاشلة.
- يجب أن تعرض لوحة التحكم عمر آخر heartbeat، ووقت آخر تحقق، وإصدار الكود، وحالة قاعدة البيانات، ومصدر الحقيقة، وسبب عدم الجاهزية.

### P2 — الأداء والاقتصاد
- تحديد سقف إنفاق للذكاء الاصطناعي والموارد السحابية والتنفيذ.
- قياس زمن الاستجابة، طول الطابور، نسبة نجاح المهام، كلفة المهمة، واستهلاك الذاكرة.
- اختيار SQLite للحالة المحلية منخفضة الحمل مع سياسة نسخ احتياطي؛ تقييم قاعدة خادمية فقط عند ظهور حاجة مقاسة.
- عدم شراء/تشغيل موارد مدفوعة تلقائيًا قبل عرض تكلفة متوقعة وموافقة.

## 5. معمارية التكامل المقترحة

المسار القياسي لكل مهمة:

1. **Perceive:** جمع طلب المستخدم والحالة الحالية المسموح بها.
2. **Understand:** تحديد الهدف والقيود والمجهولات.
3. **Plan:** خطة قابلة للمراجعة مع مخاطر وتكلفة وشروط نجاح.
4. **Authorize:** إصدار موافقة قصيرة العمر ومحددة بالعملية والموارد.
5. **Dispatch:** إرسال مهمة موقعة إلى عامل معروف وحديث heartbeat.
6. **Execute:** تنفيذ allowlist داخل sandbox بحدود زمنية وموارد.
7. **Observe:** جمع نتيجة خام ومعلومات العامل دون تعديلها.
8. **Verify:** فاحص مستقل يعيد اختبار النتيجة من خارج منفذ المهمة قدر الإمكان.
9. **Commit evidence:** حفظ الأدلة وhashes وربطها بالنسخة والمهمة والمضيف.
10. **Learn/recover:** تحديث المعرفة بعد التحقق، أو rollback عند الفشل.

**قاعدة فصل الصلاحيات:** المخطط لا يملك صلاحية التنفيذ؛ المنفذ لا يملك صلاحية اعتماد نجاحه؛ المدقق لا يغير النتيجة الأصلية؛ النشر يحتاج موافقة منفصلة.

## 6. خطة تنفيذ مرتبة حسب الأولوية

### المرحلة 0 — تثبيت خط الأساس
- تثبيت commit المصدر لكل من `main` وRender والفرع التطويري.
- جمع نتائج كل workflows وتصنيف فشل الميزة عن الفشل السابق.
- حفظ قائمة endpoints، migrations، secrets names (الأسماء فقط)، العمال والأجهزة وآخر heartbeat.
- لا دمج ولا نشر ولا تغيير إعدادات أثناء جمع خط الأساس.

### المرحلة 1 — سجل البرامج والقراءة فقط
- إكمال اختبارات registry/catalog/API والصلاحيات والمدخلات غير الصالحة.
- إنشاء عقد اكتشاف قراءة فقط يعيد OS/architecture/versions/paths/installed packages/services دون تشغيل أوامر غير مسموحة.
- حفظ دليل discovery مع host ID وtimestamp وagent version وhash.
- لا تثبيت ولا تحديث ولا إزالة.

### المرحلة 2 — عقد العامل
- توحيد التسجيل والheartbeat والقدرات وإصدارات البروتوكول.
- رفض العامل مجهول الهوية أو stale أو غير مطابق للنسخة.
- اختبارات replay/duplicate task/timeout/disconnect.
- الحفاظ على `redmi3-01` وعدم إعادة تفعيل أو حذف أجهزة دون طلب منفصل.

### المرحلة 3 — تنفيذ محدود
- بدء مهمة غير مؤذية مثل `python --version` عبر قائمة أوامر مسموحة.
- تحقق مستقل من الناتج والهوية والوقت؛ لا تعتبر نتيجة العامل وحدها نجاحًا.
- sandbox، timeouts، حد output، وnetwork policy قبل توسيع القدرات.
- بعد نجاح الاختبارات فقط يُضاف تثبيت package في بيئة اختبار مؤقتة وبموافقة منفصلة.

### المرحلة 4 — دورة تغيير البرامج
- مصدر تنزيل معتمد، نسخ مثبتة، hashes/signatures، SBOM وتدقيق تراخيص.
- Plan/diff، موافقة، backup، تنفيذ، post-check، rollback.
- فصل عمليات النظام عالية المخاطر عن مهام التطبيقات.

### المرحلة 5 — Windows Server 2025
- Preflight قراءة فقط: حساب Azure الصحيح، الاشتراك، RBAC، quota، التكلفة، الصورة والمنطقة.
- مراجعة خطة Terraform وstate والهوية والشبكة.
- نشر فقط بعد موافقة صريحة مستقلة على التكلفة والموارد.
- إثبات ARM resource + power state + guest boot + agent heartbeat + remote-access test.
- توثيق مسار الدخول الآمن قبل اعتبار المهمة مكتملة.

### المرحلة 6 — لوحة قيادة موحدة
- الحالة الحقيقية للـ API وقاعدة البيانات والعامل والـ queue والـ cloud VM.
- عرض desired state منفصلًا عن observed state.
- عرض آخر دليل، عمره، مصدره، hash، commit، وسبب الفشل.
- زر التنفيذ لا يظهر إلا مع الصلاحية والموافقة وخطة واضحة وrollback.

## 7. بوابات القبول قبل الدمج أو النشر

- [ ] جميع اختبارات ميزة البرامج ناجحة على أحدث commit.
- [ ] لا توجد بوابة CI مطلوبة معلقة أو فاشلة دون تفسير وإصلاح/قبول موثق.
- [ ] الاختبارات تثبت أن مفتاحًا غائبًا أو خاطئًا يرفض كل endpoint محمي.
- [ ] لا يمكن تسجيل برنامج على أنه مثبت أو قيد التشغيل عبر التسجيل العادي.
- [ ] لا يمكن لمرجع دليل اعتباطي أن يرفع الحالة إلى verified.
- [ ] اختبارات backup/restore وSQLite concurrency الأساسية ناجحة.
- [ ] لا توجد أوامر shell عامة أو تثبيت/حذف ضمن مسارات القراءة فقط.
- [ ] لا توجد أسرار أو قيم حساسة في logs أو responses.
- [ ] التغييرات السحابية خلف موافقة منفصلة وخطة مراجعة، لا تنفذ تلقائيًا من PR.
- [ ] نسخة الإنتاج وcommitها معروفان، وhealth/heartbeat ودليل الوظيفة يطابقان النسخة.
- [ ] Windows Server 2025 لا يوصف بأنه يعمل دون دليل guest boot حديث.

## 9. قرار التنفيذ

التنفيذ التالي الصحيح هو إكمال بوابات الاختبار، ثم إضافة اكتشاف مضيف قراءة فقط وعقد عامل موحد، ثم إثبات مهمة آمنة واحدة end-to-end. بعد ثبوت هذا المسار، ننتقل إلى إدارة دورة حياة البرامج. لا تبدأ صلاحيات التثبيت أو إدارة Windows Cloud قبل تحقق مستقل وموافقة منفصلة.
